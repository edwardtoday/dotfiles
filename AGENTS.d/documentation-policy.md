# 文档协议（扩展）

本文档定义**何时需要文档、需要到什么程度、何时必须同步更新**。

核心原则：文档要求应与项目规模、协作复杂度和行为变更风险相匹配；避免为了满足模板而制造维护负担。

## 1. 总体规则

- 文档是活文档，但只在**相关行为、接口、配置或操作方式**发生变化时要求同步更新。
- 小型脚本、个人工具、dotfiles 仓库不强制建立完整 `/docs` 体系。
- 若项目已有稳定文档结构，优先沿用现有结构，而不是机械补齐模板。
- 新增文档前，先判断它是否真的会被后续维护和使用。

## 2. 按项目规模分层

### A. 小型项目 / 脚本 / dotfiles

最低要求通常为：

- 一个可用的 `README.md`
- 必要时补充关键配置说明、运行示例或故障排查说明

适用特征：

- 单人维护
- 结构简单
- 没有复杂接口契约
- 变更主要影响本地使用方式

### B. 中型项目 / 内部工具 / 持续维护的服务

通常需要：

- `README.md`
- 必要的运行 / 部署说明
- 必要的架构说明或模块说明
- 当存在持续规划需求时，再补 `docs/backlog.md` 或设计文档

适用特征：

- 有稳定迭代
- 有多人协作可能
- 有模块边界、配置项或外部依赖需要说明

### C. 大型项目 / 多人协作 / 高风险系统

可按需建立较完整文档集，例如：

- `README.md`
- `docs/architecture-design.md`
- `docs/technical-design.md`
- `docs/backlog.md`
- 需求、决策、运行手册、迁移说明等专题文档

仅在确有读者、流程或审计需求时，才引入更正式的 PRD / SRS / RFC 模板。

## 3. 哪些变化必须更新文档

出现以下任一情况时，应更新相关文档：

- 对外行为变化
- CLI / API / 配置项变化
- 安装、启动、部署或使用方式变化
- 新增重要模块、目录结构或集成依赖
- 已知限制、风险、回退方式发生变化

如果只是内部重构，且不影响外部行为、接口或维护者理解，可不强制更新文档。

## 4. 优先更新哪些文档

默认优先级如下：

1. `README.md`
2. 与变更直接相关的操作说明 / 架构说明 / 设计文档
3. 仅在确有持续维护价值时，更新 backlog、路线图或专题文档

规则是：优先改**真正会被读到**的文档。

## 5. 对 README 的最低期待

大多数项目的 `README.md` 至少应回答以下问题：

- 这个项目是什么
- 解决什么问题
- 如何安装 / 运行 / 使用
- 关键配置在哪里
- 有哪些已知限制或注意事项（如有）

## 6. 反模式

以下做法应尽量避免：

- 为小仓库强行创建整套 PRD / SRS / 技术设计文档
- 每次微小实现细节变化都要求同步更新所有文档
- 文档标题很多，但长期无人维护
- 复制模板后长期留空，制造虚假完备感

## 7. 实践建议

- 先写最小但有用的文档，再按复杂度自然生长。
- 文档结构优先服务“未来的维护者”和“第一次接手的人”。
- 若不确定某文档是否值得创建，默认先把关键信息写进 `README.md`。
