## Question

针对 GitHub、`git.sansi.net`、Codex managed worktree、T7 canonical 仓库、语言级共享缓存、SDK 和工具链，确定每类资产的已有权威落点、隔离方式、更新方式和回收责任；临时 clone 或本机构建环境在哪些极少数条件下才合理进入临时工作区？

## Resolution

资产按“源码状态、依赖缓存、构建输出、工具链、证据、唯一检查点”分开治理；一个对象只能有一个权威落点。tmp 不再充当仓库池、缓存池或开发机镜像。

| 资产 | 权威落点 | 隔离与更新 | 回收责任 |
| --- | --- | --- | --- |
| `git.sansi.net` 仓库 | 已挂载的 `/Volumes/T7/git-sansi`，按去掉 userinfo 后的 remote URL 匹配同源仓库 | 原仓 fetch/update；需要并行隔离时由 canonical repo 创建 `/Volumes/T7/git-sansi/.codex-worktrees/<task>/...` worktree | 工作完成且状态已进入 branch/remote 后，由主仓执行 `git worktree remove/prune`；禁止直接 `rm` linked worktree |
| GitHub 仓库 | 先复用现有 `/Users/qingpei/git/github` 同源仓库；确需长期新增时也进入该层次明确的 canonical 路径 | 优先现有 repo；隔离使用 Codex managed worktree 或该 repo 的 Git worktree | branch/commit/push/MR 形成恢复锚点后受管移除 worktree，不在 tmp 保留 clone |
| Codex managed worktree | 产品自己的 `$CODEX_HOME/worktrees`，与 T7 的 `.codex-worktrees` 无关 | 由 Codex 创建、handoff 和 snapshot restore；有价值修改仍需 commit/push/MR | 完全由 Codex 产品 retention 管理，自建 cleaner 不扫描或删除 |
| 其他 Git 仓库 | 先按规范化 remote URL 搜索已有 canonical repo；缺失时进入相应长期 repo root，而不是默认进入 tmp | 同上；只读批量分析可用 mirror/object database，写入任务用 worktree | canonical owner 负责 refs 与 worktree；tmp cleaner 只处理得到明确替代引用的降级 clone |
| npm/pnpm、Cargo、uv/pip、Go、Gradle/Maven 等下载缓存 | 工具默认的用户级 cache，或后续明确配置的单一共享 cache | 以 lockfile、版本、平台和 cache key 隔离；任务只记录 key | 独立 quota + LRU；cache miss 只导致重下，不得阻断会话恢复 |
| `node_modules`、virtualenv、Cargo `target`、`build`、`dist`、coverage、测试数据库 | 所属 canonical worktree 的短期工作集，或工具原生的 keyed build cache；不是检查点 | 构建时生成，验收保存命令、版本和结果引用 | 验收取证后立即删除；纯 symlink link farm 保留，因为删除不回收包体却会破坏工具解析 |
| SDK、交叉编译器、Android SDK、不可变工具链包 | 系统/包管理器的标准位置；体积较大且需复用的版本化资产进入 `/Volumes/T7/git-sansi/.assets/<domain>/<name>/<version>`，附来源、SHA-256、平台信息 | 按版本和 checksum 寻址，不复制进每个任务；项目只保存声明与稳定路径 | 单独容量上限和最近使用策略；没有当前项目需求的完整 SDK 不应因历史任务永久留在本机 |
| bare mirror、第三方大源码镜像 | `/Volumes/T7/git-sansi/.mirrors/<host>/<namespace>/<repo>.git` | 只作为对象复用/只读来源；写入仍通过 canonical repo/worktree | 按可重新 fetch 性和最近使用独立治理 |
| CI/MR/job trace、artifact、网页/API 原始证据 | 能按稳定 ID 重取时以远端系统为权威，只保存 ID/URL/hash/结论；不可重取时进入现有报告仓库或受管 evidence store | 内容寻址、脱敏、记录来源与校验和 | 报告/证据 owner 按审计期限治理，不随 session workspace 一起保留 |
| 唯一非 Git 检查点 | 任务临时工作区中的最小 checkpoint，之后尽快交付到现有仓库或 evidence store | 明确 owner、用途、恢复命令、校验和、到期时间 | 生命周期 Module 管理短租约、可逆回收和恢复 |

### Git 状态处理合同

- clean 且 exact commit/tree 在 canonical repo 或远端可达：工作树是副本，可受管回收。
- clean 但有 local-only commit/ref：先在 canonical repo 建明确 `codex/recovery/...` 或任务分支；需要跨设备恢复时 push。项目仍活跃且修改应被评审时，优先正常 feature branch + Draft MR，而不是永久 recovery branch。
- dirty tracked/index/untracked：先判断价值；有价值内容进入 commit，必要时 push/MR。暂时不能提交时，只保存 patch/bundle、index tree、untracked 清单与 checksum 作为小检查点，不能因此保留完整 clone。
- archived、已废弃或无业务价值仓库：不因“本地有一个 commit”自动保留；确认无合规/交付义务后丢弃 recovery ref 和工作树。

### 允许临时 clone 或本机构建环境的极少数条件

只有同时满足以下条件才允许进入 tmp：canonical 存储当前不可用或不可写；任务不能等待；本机没有其他同源 canonical repo；worktree/mirror 无法满足隔离；创建已自动纳管；预计在本次活性租约内迁回或删除。T7 已挂载且可写但缺同源仓库时，应直接 clone 到明确的 T7 canonical 路径，不构成 tmp 例外。`git.sansi.net` 的真实降级 clone 在 T7 恢复后必须优先迁回，不能变成新的 unmanaged。

本机构建环境只在验证目标确实要求本机执行、远端 CI/容器/已有共享环境不能提供等价证据时按需建立；依赖声明和校验信息必须足以重建，验收后立即移除项目级环境。构建慢、下载贵或“以后可能再用”只能成为共享 cache 的理由，不能成为 tmp 长期保留理由。

### Interface 决策

资产路由是生命周期 Module 之前的 Adapter：先把源码、缓存、工具链和证据送到各自权威落点，生命周期 Implementation 才只需管理小检查点。它不应把 T7、GitHub、包缓存或 SDK 细节暴露给普通用户；普通 agent 只需遵守“复用 canonical、隔离用 worktree、状态落 Git、可再生内容不进检查点”四条规则。

本票确定类别与责任，不代表当前所有缓存路径已经配置了 quota，也不授权迁移或删除现有目录；具体迁移顺序由后续票据决定。
