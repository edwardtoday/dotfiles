## Question

定义实现前必须具备的验收矩阵：零日常手工动作、恢复成功率、物理回收时延、容量上界、unmanaged 新增率、规范仓库复用率、可再生产物驻留时间、故障降级、并发安全、迁移回滚和独立 verifier 证据分别如何测量，达到什么门槛才允许替换现有实现？

## Resolution

以下全部门槛通过，才允许新 Module 成为唯一 writer；结构检查、dry-run、单次绿测试或“目录已移入 quarantine”均不能替代对应结果。

| 维度 | 测量方法 | 通过门槛 |
| --- | --- | --- |
| 零日常操作 | 采样至少 100 个新任务及 7 天真实使用，统计 lifecycle CLI 调用 | 普通路径 `create/complete/compact/sweep` 人工调用为 0；只有明确 hold/restore/repair 计入例外 |
| 新任务可用 | 在 emergency pressure、损坏 capacity cache、T7 离线、无关 manifest 损坏和 8+ 并发创建下测试 | 100% 建立 session 关联或最小 checkpoint 路径；无预测容量拒绝，失败仅来自真实 FS/参数/锁冲突且有明确错误 |
| unmanaged | 每 5 分钟比较根目录、event ledger 与状态汇总 | 新路径 7 天内新增 unmanaged 为 0；发现漏事件后 5 分钟内自动关联，legacy unknown 只减不增 |
| canonical 复用 | 对所有 `git.sansi.net` 与 GitHub clone/worktree 记录 normalized remote、canonical path 和 fallback reason | T7 可写时 Sansi canonical/worktree 复用率 100%，tmp 完整 clone 为 0；GitHub 已有同源仓时重复 clone 为 0 |
| Git 恢复安全 | 覆盖 dirty、staged、untracked、local-only ref、detached HEAD、submodule、LFS、bare repo、linked worktree 与远端漂移 | 未形成可验证 commit/remote/bundle/patch 的任何状态均阻止主体删除；受管 worktree 只由主仓移除 |
| 可再生产物驻留 | 完成取证并释放最后进程/FD 后计时，核对 allocated bytes | 15 分钟内回收；稳定态残留不超过 1 GiB；symlink-only link farm 0 误删 |
| 主体收缩时延 | RecoverySet 验证完成后计时 | 15 分钟内物理回收工作区主体，不以 72h/7d/14d 延迟；报告实际回收 bytes |
| 恢复 | fault-injection + 至少 20 个 legacy 样本，覆盖自动 resume、手动 restore、quarantine、checkpoint checksum、引用在线与 T7 离线 | verified 引用可用时主体重建成功率 100%；唯一 checkpoint bit-for-bit 恢复 100%；引用不可用时 100% fail closed、原对象不变且 blocker 可见，不计入“可重建成功率”分母 |
| 容量 | 每 5 分钟采集 tmp、checkpoint、quarantine、reclaimable、evictable retention、in-use、irreducible blocked allocated bytes | `evictable_retention_bytes` 始终不超过 5 GiB，reclaimable 稳态不超过 1 GiB；总量目标 10 GiB。超过 20 GiB 后 15 分钟内清空全部安全可回收字节，余量 100% 归入 `in-use` 或 `irreducible_blocked_bytes`；不以删除不可替代数据强行满足总量目标 |
| Hold | 创建、续期、过期、clear 和容量压力测试 | 每个 Hold 都有 owner/reason/expires_at，最长 30 天；只保护 checkpoint，不保护可再生字节；过期后下一轮自动重评 |
| 并发与崩溃 | 在 hook ingress/drain、reconcile、rename、fingerprint、quarantine、restore、purge、ledger write 各阶段注入 crash/race | 无双 writer、无丢 heartbeat、无路径替换误删；重启后自动 reconcile；稳定 task-lock inode 不被不安全 GC |
| 后台自然发生 | 用唯一 canary 做真实端到端测试：先核对 hook command ack；再停用 hook，由当前 loaded LaunchAgent 在 5 分钟内处理 canary；最后真实 unload/load 或重启后重复 | 两条 Adapter 路径都产生对应 canary ack；核对 loaded plist、实际进程所用脚本 inode/版本、运行时间和 exit status，不能用静态 plist或历史日志替代；后台失败不阻断对话且 status 显示滞后 |
| 迁移与回滚 | 新旧 ledger shadow compare、ownership/cutover race 注入、切换 writer、故意回滚到旧 Adapter | 双读差异有保守解释；任一 task/generation 同时最多一个 writer；回滚前能停 dispatcher并排空旧进程/队列，之后旧 CLI 能读取全部未完成任务，quarantine/checkpoint 可恢复 |
| 安全与隐私 | 扫描 remote URL、evidence、日志和错误输出 | userinfo/token 不落日志或报告；权限为私有；任何凭证暴露只报告位置与轮换要求，不输出值 |
| 独立 verifier | verifier 只接收原始证据、待验产物和 rubric，独立复算 | 高风险删除批次、writer 切换、恢复与容量结果均有独立通过结论；执行者摘要不能作为证据 |

### 替换门禁

1. 单元/集成/fault-injection 全绿只是第一层。
2. 新任务 shadow 7 天、new-only writer 7 天、唯一 writer 14 天三个观察窗必须依次通过；窗口内出现数据损失、未归因容量、重复 sweeper 或 admission 拒绝即重置该窗口。
3. legacy 迁移允许在唯一 writer 后继续，但必须有完整 `workitems.tsv`；未迁项只能是有 owner、字节数、blocker 和复核时间的显式例外。
4. 最终 closeout 必须报告：起止 allocated GiB、各类剩余字节、实际回收时延、恢复抽样、Git 远端验证、LaunchAgent/hook readback、rollback 演练和剩余风险。

达到这些门槛后，旧 `codex-tmp` 才可从兼容 Adapter 降为离线 repair 工具；否则继续双读，不宣称迁移完成。
