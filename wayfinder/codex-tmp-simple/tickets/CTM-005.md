## Question

在官方恢复能力、真实内容分层、复杂度来源和资产路由都明确后，选择一个最小领域模型、状态机和用户操作面：哪些动作完全自动发生，哪些异常才需要 `keep`、`status` 或 `restore`，系统如何保证新任务永不因规划容量被拒绝，同时又能让实际磁盘占用回到目标范围？

## Resolution

选择“事件驱动 reconcile + 内容验证”的深 Module。Codex hook 和 LaunchAgent 是同一事件 Interface 的两个 Adapter：hook 提供及时的 session/cwd 事实，LaunchAgent 补偿漏事件并推动后台收敛。纯扫描只作为发现 legacy 与故障兜底；显式 CLI 只作为异常和迁移 Adapter。

### 被比较但未采用的 Interface

1. 显式 checkpoint registry：agent 调用 `register/complete/release`，系统只管理已登记对象。它灵活、容易测试，但调用遗漏会继续制造 unmanaged，日常操作不为零。
2. 纯内容扫描器：后台根据目录、Git、进程和 mtime 自行分类。它对调用者最省事，但无法仅凭文件推断“是否唯一、是否已经交付”，会把业务判断藏进不可靠启发式。
3. 事件驱动 reconcile：Adapter 提交 session/process/filesystem 观察，Module 结合恢复引用和内容验证得出动作。它把复杂度集中到一个 Seam，漏事件可由扫描 Adapter 修复，默认路径无需用户参与，因此采用。

### 最小领域模型

管理单位不再是“整个任务目录”，而是：

```text
WorkspaceObservation = session/thread + cwd + lease + discovered content
RecoverySet = verified canonical refs + optional small checkpoint
Hold = reason + owner + expires_at
ReclaimDecision = removable bytes + blockers + next evaluation
```

活性租约只保护正在使用的工作集；恢复引用只证明对应内容可替代；例外保留只延长最小 checkpoint 的期限。任何一个字段都不能保护目录里的所有字节。

### 状态机

用户只看到四种汇总状态：

- `in-use`：有新鲜活性租约或进程/FD 引用；仍可清理已验收的可再生产物。
- `settling`：租约已结束，后台正在归位 Git、剥离输出并生成最小 RecoverySet。
- `recoverable`：大主体已物理回收，只剩可自动恢复的小 checkpoint/quarantine。
- `blocked`：存在 dirty/local-only Git、未知唯一内容、失效恢复引用、打开进程或验证错误；必须显示 blocker 和字节数。

`removed` 只留在审计记录，不是长期状态。`Hold` 是带到期时间的正交属性，不新增永久 `keep` 状态。`compacting/purging/incomplete` 等事务阶段仍可存在于 Implementation 的 crash journal，但不进入普通 Interface。

### 自动流程

1. SessionStart/首次 cwd 观察只建立很小的 session 关联；不做容量 admission，不预留 GiB，也不要求每个任务先创建大目录。
2. 文件出现后先按资产路由分类。canonical Git/worktree、用户级 cache、T7 asset 和远端 evidence 不归 tmp 生命周期所有。
3. Stop/SessionEnd、租约超时或 LaunchAgent 扫描触发 reconcile。进程/FD 消失后，可再生产物在同一轮物理删除；Git 只做只读分类与恢复性验证。dirty、local-only 或价值未决状态默认进入 `blocked`，reconcile 不自动 commit、push 或创建 MR；最多生成并校验本地 patch/bundle 检查点，且在其恢复完整性证明通过前保留原对象。唯一非 Git 内容提取为最小 checkpoint。
4. RecoverySet 验证通过后立即移除工作区主体，不再先等 72 小时或 7 天。恢复窗口只保护小 checkpoint：默认 7 天；前 24 小时可直接自动恢复，之后仍可从 quarantine 恢复。
5. session resume 指向 recoverable checkpoint 时自动恢复并续租；失败则保持原对象且报告 blocker。
6. Hold 必须含理由和绝对到期时间，默认最多 30 天；续期是新的显式决定。Hold 不保护 clone、cache、SDK 或 build output。

### 用户和 agent Interface

- 日常用户与普通 agent：零个生命周期动作。
- 只读 `codex-tmp status [task]`：按 `reclaimable/protected/blocked` 字节、恢复引用和预计动作展示，不暴露事务细节。
- 异常 `codex-tmp hold <task> --until ... --reason ...`：只保留最小 checkpoint；可提前 clear，不能无期限。
- 异常 `codex-tmp restore <task>`：恢复仍在窗口内的 checkpoint；session resume 仍优先自动执行。
- `event/reconcile/migrate/repair` 为隐藏或管理员 Interface；旧 `create/active/keep/complete/compact/...` 只在迁移期由兼容 Adapter 接受。

### 容量结果合同

“新任务永不因规划容量被拒绝”和“任意活跃任务都能无限写且磁盘绝不超过阈值”不可同时保证。新方案保证前者，并对生命周期拥有的**非活跃保留量**给硬边界，对活跃或安全阻塞字节给显式账单：

- 新 session、目录关联和观察事件在 capacity cache 损坏、T7 离线或压力为 emergency 时仍不得因预测/配额拒绝；只有真实文件系统错误可失败。
- 可再生产物在进程/FD 释放且取证完成后 15 分钟内回收，稳定态残留不超过 1 GiB。
- 已验证可替代、达到最短恢复期且可安全淘汰的 inactive checkpoint/quarantine（`evictable_retention_bytes`）本机合计硬上限为 5 GiB；单个普通 checkpoint 目标不超过 256 MiB，超过 512 MiB 必须标为 blocked 并立即给出外部交付路径，不能静默变成永久例外。
- `~/.codex/tmp` 总量目标 10 GiB、压力线 15 GiB、紧急线 20 GiB。超过 20 GiB 后后台仍不拒绝新任务，但必须在 15 分钟内清光所有安全可回收字节，并把剩余量 100% 归因到 `in-use` 或具体 blocker；不得留下“unmanaged/unknown 因此无限保留”的暗账。
- quarantine 使用 7 天默认恢复窗口；若 5 GiB 硬上限受压，只能从已验证可替代、已过最短 24 小时的对象中最旧优先淘汰，并保留删除审计。不可替代 checkpoint 计入单独的 `irreducible_blocked_bytes`，不受 5 GiB 可淘汰保留量上限驱动删除；它可以令总量超过目标，但必须告警、给出 owner/退出路径并持续重评，不能伪称总量有硬上限。

这个合同只对系统能安全淘汰的保留数据承诺硬边界；`in-use` 与 `irreducible_blocked_bytes` 是显式例外，只有可观测、可追责和时限目标，没有以误删换取的伪硬上限。它让无法自动压缩的活跃/唯一数据成为可见异常，而不是用 admission 拒绝新任务掩盖问题。

本票定义目标 Interface 与语义，尚未实现；迁移期间旧 CLI 和 manifest 必须继续可回滚读取。
