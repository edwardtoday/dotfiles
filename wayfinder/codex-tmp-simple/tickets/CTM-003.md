## Question

结合 `codex-tmp` 的命令面、状态机、配置、测试、后台任务和本会话历史，哪些复杂度来自真实安全约束，哪些来自职责混杂、重复记录或补丁叠加；用户与普通 agent 实际必须执行和理解的动作最少可以缩减到什么程度？

## Resolution

当前实现的问题不是“安全检查太多”，而是把安全删除引擎、session 活性、恢复包存储、scratch 租约、可再生产物清理、容量预测和 legacy 迁移都暴露成了同一个浅 Module。CLI parser 已有 21 个子命令（含隐藏的 hook 入口）、27 个配置项和多个相互嵌套的状态集合；实现则已有 3540 行、133 个函数和 105 项测试。这个 Module 的 Implementation 很大，但 Interface 也几乎同样大，Depth 不足。

### 必须保留在 Implementation 内的安全复杂度

- 删除前必须检查路径 containment、符号链接、mount/device、inode/identity 和目录内容稳定性；删除过程必须原子迁移、可重入并能在崩溃后 reconcile。
- dirty Git、远端不存在的独有提交/ref、linked worktree、进程 cwd 和打开的文件描述符都必须阻止物理删除。Git 检查必须只读，并在最终删除快照前重验。
- session heartbeat 与最终删除必须线性化；已排队或并发到达的恢复事件优先于删除。误判后需要一个短期、可逆的 quarantine/restore 窗口。
- 可再生产物只能在分类确定后清理。纯符号链接 `node_modules` 必须保留，local/mixed `node_modules`、Cargo `target` 等才可回收；遍历失败必须 fail closed。
- 后台工作必须限量、低优先级、并发互斥且失败可重试。新任务创建必须在容量信号失效或磁盘压力高时仍成功，容量只影响清理紧迫度，不能成为 admission gate。

这些规则有真实误删和恢复事故支撑。它们应该形成一个深的回收 Module：调用者只提交“观察到的任务状态”，Implementation 自己完成判定、迁移、重验、回滚和重试。测试也应主要穿过这个 Interface 验证可观察结果，而不是让每个内部事务都变成调用者要懂的命令。

### 来自职责混杂和补丁叠加的复杂度

- `active`、`keep`、`complete` 是用户意图状态；`pending`、`compacting`、`compact_incomplete`、`compacted` 是恢复包事务状态；`quarantined`、`purge_pending`、`purging`、`purge_incomplete` 又是删除事务状态。它们共用或嵌套在 manifest 中，导致“任务是什么状态”没有单一答案。
- `compact` 为了提前回收又建立 SHA-256 对象、引用账本、发布事务和单独 GC，实质上在 tmp 管理器内再造了一套检查点存储。它解决了过长保护期造成的容量问题，却把错误的内容长期放进 tmp 这一上游问题留在原处。
- `scratch-acquire/check/release/clean` 把并发临时写入协议变成公共 Interface；普通任务被迫理解 fencing token 和 generation，而这些应是专用 scratch Adapter 的内部协议。
- budget class、expected peak、reservation、三组容量水位和 cache 只产生告警，不约束写入，也不保证回收结果。它们增加了配置与解释成本，却没有形成容量上界。
- `adopt`、`refresh-fingerprint`、`migrate-legacy-compaction`、`release-checkpoint` 和 `recovery-gc` 都是迁移或维修命令，不应出现在普通 agent 的操作手册中。
- hook 会启动后台 maintenance，LaunchAgent 每五分钟也运行 maintenance；同时存在 hook queue、全局锁、多种专用锁、sweep throttle 和两套触发路径。并发保护有必要，但触发与调度责任重复。
- 当前状态分散在 manifest、`sessions.json`、capacity cache、recovery references、transition records、history 和 quarantine manifest 中，诊断时需要跨多个载体拼接。同一事实的可派生观测缓存和 history 可考虑合并，但 recovery ledger 与 manifest 的双向 reconcile、rename transition journal、quarantine manifest 和稳定 pathname 的 task lock 是崩溃恢复或并发线性化所需的安全冗余，不能因文件数量多而删除或随意 GC；task lock 只有在 generation 和 holder 安全均可证明的协议下才能回收。

从 Module 设计看，真正的外部 Seam 应位于“任务事件进入统一 reconcile”处。Codex hook 和 LaunchAgent 是两个真实 Adapter：前者提供及时事件，后者提供漏事件后的最终一致性。安全删除、恢复事务、锁和 legacy 兼容都属于内部 Seam，不应继续膨胀 CLI Interface。

### 最小可理解操作面

- 用户日常操作：**零**。不需要选择 budget、运行 sweep、判断 complete、手动 compact 或批准后台回收。
- 普通 agent 日常操作：**零个生命周期命令**。它只需遵守资产路由：规范 Git/worktree、共享缓存和已交付产物不进入 tmp；只有唯一且尚未交付的非 Git 检查点才放入任务临时工作区。任务创建、owner 关联和结束观察由 Adapter 自动完成。
- agent 唯一例外动作：对确实暂时不能回收的唯一检查点执行一个带理由和到期时间的“保留”语义；保留必须自动到期，不能成为无限期容量豁免。
- 用户唯一异常动作：查看统一状态并恢复最近一次可逆回收。维修、迁移、GC、fingerprint、scratch token 和事务状态只属于运维诊断面。

因此，后续“最小生命周期和用户操作面应该是什么”应以 **日常零动作，异常只理解“限时保留”和“恢复”两个概念** 为 Interface 上限；不是把现有 21 个命令重新命名。现有安全校验可以保留甚至加强，但要下沉进一个更深的 Module。现有 manifest 与命令只作为迁移兼容层，由“现有 codex-tmp 如何无损迁移到最小实现”决定退役顺序。

### 证据边界

- 结论来自当前 `bin/codex-tmp`、`tests/test_codex_tmp.py`、`bin/TOOLS.md`、hook、LaunchAgent、lifecycle config 和本会话已发生的 admission、link-farm、过长保护期及 unmanaged 故障记录。
- 本票没有修改清理器、配置或真实 tmp 内容；没有验证新 Interface 的实现可行性。状态机细节、容量目标和迁移步骤仍分别留给后续票据。
