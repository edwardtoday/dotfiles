## Question

从当前 manifest、hook、LaunchAgent、quarantine、recovery package、scratch fencing 和 legacy unmanaged 状态迁移到最小实现时，哪些能力保留、下沉、合并或退役；如何分阶段双读/兼容、回滚和处理旧目录，避免再次丢失 session 恢复依赖或长期维持两套状态机？

## Resolution

迁移采用“先路由、再双读、先新后旧、按门晋级”，不做一次性重写或全量删除。每个阶段都必须能通过切换 LaunchAgent/CLI Adapter 回到上一阶段；旧 manifest 在迁移完成和恢复窗口结束前不删除。

### 能力去向

| 现有能力 | 去向 |
| --- | --- |
| containment、Git/remote、process/FD、fingerprint、final fence、原子 move、crash reconcile | 保留并下沉到 Reclaim Implementation |
| hook queue 与 LaunchAgent | 合并为同一事件 Interface 的实时、补偿两个 Adapter |
| `active/keep/complete` | 双读期映射为 lease、Hold、settling 观察；最终退役 |
| quarantine/restore | 保留，但只承载小 checkpoint，默认 7 天 |
| recovery package/reference/GC | 只在旧 compact 和确需本地 checkpoint 时作为内部兼容；新对象优先直接形成最小 RecoverySet，稳定后退役旧发布协议 |
| scratch fencing | 从公共 CLI 下沉到需要多 writer 的内部 scratch Adapter；普通任务不接触 token/generation |
| budget/reservation/admission | 删除 admission 语义；保留实际容量测量与压力触发 |
| adopt/unmanaged | 新路径改为事件观察自动关联；legacy 只读识别后逐项迁移，不再批量标 active |
| refresh/migrate/release/GC 等维修命令 | 移入管理员 repair Interface，迁移结束后从普通帮助移除 |

### 分阶段顺序与门槛

1. **冻结基线。** 保存当前脚本、配置、plist、测试结果和真实 inventory；记录 live inode/安装路径。新增行为测试，不动真实目录。门槛：当前 105 项测试、LaunchAgent readback 和 link-farm/admission 回归均通过。
2. **先落资产 Router。** 更新共享规则和任务入口，使 Sansi/GitHub/caches/assets 在写入前进入 canonical；T7 可写但缺同源仓时直接 clone 到 T7。门槛：连续 7 天新 Sansi 任务无 tmp 完整 clone，T7 降级都有原因与迁回期限。
3. **引入新 ledger，双读双写。** 新 Reclaim Module 以旧 manifest + 新 observation ledger 计算 decision，但只 shadow 报告；旧 CLI Adapter 同时更新两者。任何不一致按更保守结果处理。同时先给 legacy engine 增加并验收 ownership fence：每个任务有 `lifecycle_owner=legacy|v2` 与 generation；两边必须在同一个稳定 `ownership.lock` 下 claim，并继续复用相同 per-task deletion lock。legacy engine 遇到 `v2` 必须跳过全部写入和删除。门槛：至少 100 个 synthetic case 和全部真实目录 shadow compare 无“新方案更激进且无解释”的差异，旧版本对 `v2` ownership 的 fail-closed 测试通过。
4. **原子切换并只接管新任务。** 暂停 LaunchAgent dispatcher，取得全局 lifecycle/ownership fence，封存并排空 hook queue，等待旧 maintenance PID 退出，写入带 generation 的 cutover marker，再原子替换 dispatcher 并 reload。此后只有一个 LaunchAgent dispatcher：按 task owner 调用 legacy 或 v2 engine；hook 只入事件队列，不自行启动 sweep。新任务在共享 ownership lock 下先原子 claim 为 `v2`，旧任务保持 `legacy`；任一 owner/generation 缺失或冲突均 fail closed。先物理清理可再生产物，再收缩有 verified RecoverySet 的主体。门槛：race/fault injection 证明任一路径任一时刻最多一个 writer，7 天无新增 unmanaged、恢复演练通过、容量/时延达标。
5. **迁移 legacy，按 `workitems.tsv` 小批推进。** 优先级依次为：clean 且 T7/remote 同 HEAD/tree 的 clone；无进程引用的 build/cache；ownerless auto-adopt；已完成且有 verified recovery refs；dirty/local-only/未知。每项记录 size、owner、Git、process、替代来源、计划动作、回滚点和 verifier。linked worktree 只经主仓移除；dirty 状态先 commit/push/MR 或生成最小 bundle/patch。每批先独立 verifier，再 quarantine/受管删除，再核对实际 GiB。
6. **切换全部任务到唯一 writer。** 新 Module 连续 14 天通过验收后，在同一 ownership fence 下逐项把 legacy owner 原子迁为 `v2`；LaunchAgent dispatcher 与 hook 只写新 ledger，旧 CLI 仍可读并映射但不能 sweep。回滚必须先停 dispatcher、排空旧进程/队列，再把尚未物理迁移的 owner generation 切回；不能只换可执行文件。
7. **退役兼容状态。** 最后一个旧 quarantine/recovery reference 到期并通过恢复抽样后，才删除旧 command、reservation、compaction/scratch 公共 Interface。旧 manifest 归档为只读迁移证据；repair 工具保留一个版本周期。

### 提前回收与回滚

- 不再让数 GiB 主体等待 72h + 7d + 14d；可再生产物在进程释放后 15 分钟内删除，有 verified canonical refs 的主体在同一 reconcile 周期收缩。长窗口只保护小 checkpoint。
- 任何 move/delete 前记录 source inode/device、tree/fingerprint、Git refs、恢复引用和目标；物理删除前再次验证。迁移采用 quarantine 或同设备 tombstone，直到对应阶段验收通过。
- 回滚不尝试“重建被证明可再生的 build output”；它恢复的是 checkpoint、manifest/ledger writer、LaunchAgent 版本和尚在 quarantine 的主体。已迁入 canonical Git/T7 的内容按记录引用恢复。
- symlink-only `node_modules`、活跃 VM/进程 FD、T7 linked worktree、dirty/index/local-only Git 和校验失败项始终 fail closed。

迁移完成的定义不是“新脚本已安装”，而是唯一 writer 已切换、旧状态不再新增、legacy 清单清零或全部转为有期限 blocker、容量结果持续达标且旧实现可以退役。
